## Answer

### 1. Both premises are withdrawn

**A-012 §1.3 — "the approved A is fixed-year" — is false.**
`docs/contracts/P_R5CYCLE_OPTIONS_DRAFT.md:60` reads "For A/B, check every
V3-admitted year 1900–2100, not only the outer query year", and the decision
table says all 201 years. The all-years scope is the approved proposal, not a
strengthening selected during installation. I took "fix y" from the Q-011 menu
sketch, which the approved draft supersedes. There is consequently **no new
stated limitation to record** beyond the same-birthday exclusion and the
conservative all-years exclusion the draft already carries and which Q-013 says
will be documented.

**A-012 §1.5 — "the audit was case-year-only" — is false.**
`phase1-decision-audit/birth_audit.pl:103` computes, for every K edge,
`findall(Y,(between(1900,2100,Y),once(user:s152_c_3(D,T,Y))),Years)` and records
`c3_success_years` per edge. The corpus result is year-complete as run, so
`summary.json`'s 376/376 with no refined-A failure and `MENU_GRAPH_CHECK.json`'s
75,576 K-and-c3 graphs already cover the installed scope. **No re-run is owed.**
The 2018 probes on the two fixtures are separate bounded-recursion diagnostics
and were not generalized. One observation rather than an objection: `DecreaseA`
as written at draft lines 78–82 is year-independent while `L_y`'s eligibility is
year-indexed, so whether the aggregation applies the condition to all K edges or
only to edges with a non-empty success-year list, the reported "no failure"
result is safe in either direction — stricter in the first case, exact in the
second.

A-012 §1.4's union-of-years form is therefore moot; Q-013 confirms the actual
conjunction is used, and I withdraw it as an implementation suggestion.

### 3. Does a new owner decision remain? One, and it is contingent

No unconditional one. The installation as scoped — uniqueness half, all-years
conjunct, dependent checked time interface, everything else recorded as a
prerequisite — is execution of decisions Dev has already taken. It also cannot
make any check pass that was not already blocked: with no `OracleGuards`
instance, neither `Valid` nor `ValidStip` evaluates at all, so adding a third
required field changes nothing that could be falsely certified in the meantime.

There is one contingent decision, and Q-013 asks it to be isolated with a
concrete uncovered call, so:

**The call.** An original case whose appended stipulation clauses supply a
statute predicate with a year argument outside 1900–2100 — or a stipulated
Workday string whose `YYYY` prefix is outside that range, reaching
`s3306_c_10_A_ii` at `section3306.pl:717-719`, which derives the year from that
string. The pinned interpreter evaluates such a call normally and returns an
ordinary answer. The Lean wrapper cannot construct `CoveredR5Time`, so it reports
a coverage/domain failure, which is correct under draft line 66. The input is now
admitted but ungradable: `ValidStip` lets it in, because `Stip.wellFormed` is
`s.args.length == s.pred.arity` (`Interface/Household.lean:324`) and `v3` inspects
`f.days` for facts only, while PARITY.md classifies a side with no comparable
value as an infrastructure failure, so parity has not passed for that section.

**Why the approved boundary does not determine the handling.** The draft says
what the wrapper must not do (fall back to a value) and what an admitted
execution owes (prove the failure path unreachable). Unreachability has to be
proved *from the admission predicate*, and for the originals that predicate is
`ValidStip`, which does not constrain stipulation arguments at all. So if an
admitted original carries an uncovered year, the proof is not merely outstanding
— it is unavailable, and the choice between excluding the case from the graded
domain and admitting it as permanently ungradable is a domain decision that only
Dev can take. Neither option is implied by the text: the first changes what the
376-case gate ranges over, the second means that gate cannot reach zero.

**Why it is contingent, and how to discharge it today.** For generated inputs the
question is empty: V1 forces `stipulations = []` and V3 bounds every fact day, so
no uncovered year can arise. For the originals the trigger is a measurement, not
a judgement, and it can be taken guess-free without assigning field roles: scan
every stipulation argument in the 376 for an integer that looks like a year and
lies outside 1900–2100, and for any `YYYY-MM-DD`-shaped string whose year is
outside that range. If nothing matches — which the corpus makes very likely —
then no role assignment can produce an uncovered call, the failure path is
unreachable for the frozen originals as a measured fact, and **no owner decision
is needed**. If something matches, the choice above is forced and should go to Dev
with the case ids. The audit harness already parses every case clause, so this is
a filter over data it holds.

That measurement is the one thing I would add to the obligation list, and it is
cheap enough to take before the installation is staged rather than after.

## Rationale

The useful output here is the boundary between "Dev must choose" and "we owe
work", because the failure mode of this phase is asking Dev to approve the same
proposal twice and thereby making an approved decision look unsettled. On the
two premises I had it wrong: the draft text and the audit program both say
plainly what Q-013 says they say, and the escalation they supported dissolves.

What survives is narrow and worth the words: the approved text tells the wrapper
never to invent a value and tells the implementation to prove the failure path
unreachable, but unreachability is relative to an admission predicate, and for
the 376 that predicate does not constrain stipulation arguments. That is not a
hole in the decision; it is a place where a measurement decides whether a
decision is needed. Taking it now costs a filter over data the audit already
holds, and not taking it risks discovering at the Week-1 gate that an admitted
original cannot be graded and that the remedy is a domain change made under
schedule pressure.
