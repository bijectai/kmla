## Question

Please answer each part with its basis in `human/DECISIONS.md` or `Interface/`,
or escalate it to Dev with a proposed minimal owner decision. Both implementation
lanes read A files, so please put no harness or oracle code, constants,
algorithms or file contents in the A.

1. **Where the declaration lives.** Should the output positions go in
   (a) a new per-mode field in `Interface/TIME_SCHEMA.json` (for example, output
   positions for each listed case mode). That field would be rendered into
   `Interface/QuerySchema.lean` by `scripts/check_time_schema.py` and checked
   there, next to the existing lexical H6.5 completeness check. Or should they go
   in (b) a separate Interface file with its own generated Lean table and check?
   Please also confirm the scope: only the case modes listed in H6.5 for the 135
   signatures. H6.5 says the oracle translator adds statute-internal modes clause
   by clause (G2), so the shared declaration would not list those.

2. **Which positions are outputs.**
   - G2 (`human/DECISIONS.md:33-40`) makes output positions "the rest" after the
     positions bound at every call site.
   - H6.5 (`human/DECISIONS.md:913-916`) adds: "A `b` in a position that the
     `% Question` text presents as the answer (e.g. the `4000` in
     `s151_a(alice,4000,2015)`) is an output position."
   - H6.1 types each target "with the output positions as the result tuple".
     H6.3 scores a case by "the expected tuple (the ground values of the case goal
     in output positions, or 'non-empty' if none)".

   For each queried signature and listed mode, which positions are outputs?
   Specifically, where a case mode binds a position (`b`) that the case's
   `% Question` presents as its answer, which positions does the signed text make
   outputs? And for which signatures or modes does the signed text leave the
   choice open, so that it needs Dev?

   Examples from the evidence file, listing the case goal against its question:
   - `s1_a_i(17330,2600)` against "have to pay $2600 in taxes ... under section
     1(a)(i)";
   - `tax(alice,2019,0)` against "How much tax does Alice have to pay in 2019? $0";
   - `s63_c_1(alice,2017,5000)` against "Alice's standard deduction in 2017 is
     equal to $5000".

   Some rows bind only identifiers or years, for example
   `s3306_b(_,alice_pays,alice_employer,alice,bob,alice,bob,_)`. Some have
   `f` positions and extra conjuncts (the `s152_d_2_D/G` and `s68_b` cases).

   The builder has not inferred outputs from `b`/`f` alone, chosen modes or
   guessed. A per-signature table, or a per-class rule that names its
   signatures, is what the builder needs to fill in the declaration.

3. **The harness's hand-coded projection exceptions.** HANDOFF item 1 says to
   "move the harness's hand-coded projection exceptions into" the shared
   declaration. This integration context has not opened `harness/` or `Oracle/`
   and must not receive either lane's implementation. How should those
   exceptions reach the declaration? Three options the builder can see:
   - the governor names, in contract terms only, the signatures and positions
     they concern and the DECISIONS text that governs each;
   - Dev, or a fresh harness-lane session, produces that list;
   - the declaration is derived from DECISIONS alone, and the harness lane then
     conforms and reports any difference as a finding.

   Is one of these required, or is there another route?
