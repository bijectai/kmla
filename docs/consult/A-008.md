# A-008

## Answer

### 1. The encoder defect: restoration, builder-owned, fix it now

**Classification: a defect in builder-owned code against an already-approved
requirement.** Not a semantic question, not a contract amendment, not grounds to
touch `Valid`, `gen/`, the owner meter or any corpus.

`human/DECISIONS.md` H6.2 requires that "both sides map each solution to JSON",
and `docs/contracts/PARITY.md` requires "UTF-8 JSON" envelopes and makes
malformed JSON exit 2. JSON does not permit an unescaped U+0000–U+001F inside a
string, so `Interface/Household.lean:639` emits something that is not JSON. It
fails H6.2 on H6.2's own terms. Escaping the control range restores the approved
requirement and changes no semantics: the set of representable values is
unchanged, and every string that already encoded validly encodes to the same
bytes.

The root cause is the docstring's own premise — "the corpus contains no control
characters". True of the 376 originals, false of the population the encoder
actually serves. V1 constrains `Term` strings to *non-empty*, not to
control-free, so a `Valid` generated household may carry `atom "a\nb"`, flow into
an observation, and produce a record the meter must reject under PARITY.md's
malformed-JSON clause. The exposure is reachable at Checkpoint 2, not
hypothetical, and it would present as a producer or meter failure rather than as
an encoder bug.

**Timing and ownership: yes, correct it now.** `Interface/` is Astra's per
`docs/PLAN.md` §3, and it is the one artifact both isolated lanes legitimately
share (§2: "pass them only DECISIONS.md and Interface/"). Fixing the shared
encoder before either producer exists is the only way to keep the two lanes
byte-aligned without them communicating, and doing it after either lane has
encoded anything would mean changing bytes both lanes had already committed to.
The ownership line inside `Interface/`: code that makes the file match the signed
semantics is restoration; anything that alters a signed claim — `Valid`, V1, the
H6.2 tag vocabulary, the observation's set semantics — is an escalation. This is
the first kind.

**Scope of the fix, stated precisely so the bytes are pinned.**

- Escape `"`, `\`, and U+0000–U+001F. Leave every code point ≥ U+0020 other than
  those two as raw UTF-8. That second half is not optional: it is what makes the
  fix byte-preserving for all existing encodings. Switching to `\uXXXX` for
  non-ASCII would also produce valid JSON but would change bytes that are already
  correct.
- Pin which spelling each control uses, in the docstring, because the encoded
  string is not merely transported — `observe` *sorts* on it. Two engines that
  escape U+0009 differently produce differently ordered observation arrays, and
  PARITY.md's "arrays retain order" turns that into a parity mismatch with no
  semantic cause. Recommended: the short forms `\b \f \n \r \t` and `\u00XX` for
  the remaining controls, which is what a standard JSON emitter produces, so the
  Prolog-side serializer gets byte compatibility from its library rather than
  from a hand-written mirror.
- Two latent divergences of exactly the same class, not yet triggered, worth
  pinning in the same docstring while it is open: `Obs.encode` emits `{"a":"…"}`
  with no space after the colon, where a default `json.dumps` emits `{"a": "…"}`;
  and it passes non-ASCII through raw, where a default `json.dumps` emits
  `\uXXXX`. Neither affects the meter's structural comparison, but both affect
  the sort order that `observe` computes inside each engine. The serializer lane
  needs `separators=(',', ':')` and `ensure_ascii=False` to match.

**Regressions.** Every control character 0x00–0x1F survives encode → real JSON
parser → equal value; the nesting cases (`arr`, `Solution.encode`) too; sort and
dedup stability under `observe`. Add the byte-identity check against the full
corpus observations as a golden test once Phase 1 produces them — it is the
direct evidence for "valid existing encodings preserved", and it cannot be run
today.

**The rejected alternatives, named so nobody reaches for them later.**
Constraining `gen/` to control-free strings is filtering inputs to make a check
pass, which `docs/PLAN.md` §2 forbids outright. Tightening V1 to exclude control
characters is editing a signed artifact to accommodate a bug in code. Both would
convert an encoder defect into a permanent narrowing of the input population, and
the narrowing would be invisible in the results.

### 2. Input wire spelling: builder-owned codec, with one clause to release and two items that are not codec choices

**Governing text.** `docs/contracts/PARITY.md`, File envelopes: "The approved
`Interface/` and `DECISIONS.md` will define section payloads and query encodings.
That definition remains pending; the independent meter only needs the input
identity and section to determine the expected output population." And Comparison
requirements: "Both engines must implement only approved canonicalization before
emitting outputs. Until the payload and result specifications are approved,
producers are blocked rather than guessing representations."

Read that clause literally: it is conditional and it names its own release
condition — approval of `Interface/` and `DECISIONS.md`. It does not reserve a
further, separate approval of a wire schema. The condition is now discharged:
`human/DECISIONS.md` carries signed G4, H1, H2, H3, H4, D1/V9, M1, H6.1, H6.2 and
H6.5, and `Interface/Household.lean` is installed and type-checks on the pinned
toolchain. **So the answer is: the concrete JSON spelling is a builder-owned
lossless codec of an approved shape, and no further semantic approval is
outstanding for the fields those sections determine.** This is not a general
phase authorization waiving a specific block; the block's stated condition is
met on its own terms.

What the signed text determines, leaving only spelling:

| Wire element | Fixed by |
| --- | --- |
| Facts list: source order, duplicates kept, nothing keyed/sorted/defaulted | H1, F13 |
| One wire form per `Fact` constructor, named by its source predicate | H3 |
| Argument kinds per position; `amount_` int, `start_`/`end_` a `Day` | H2 |

Reusing H6.2's tag vocabulary on the *input* side is a codec choice, not a new
semantic mode: H6.2 fixes those tags for the same `Term` domain G4 already fixes
for facts, so reuse invents nothing and keeps one vocabulary in the interface.

**One clause must still be released, and it is Dev's.** PARITY.md's sentences
still say "remains pending" and "producers are blocked". Those are now stale, and
a stale blocking sentence is not something the builder should quietly edit while
installing P-PARITY5 — it is the sentence that gates producing any output at all.
I have recorded the release as **P-WIRE (PROPOSED)** in `docs/DECISION_LOG.md`
with the proposed substance and without proposing wording; Dev approves the text.
It is filed as `PROPOSED`, not `PENDING`, so `verify_phase0.sh:205` does not
reopen the signed-off Checkpoint 0 gate over a Phase 1 item.

**The narrow field that is genuinely not determined: record granularity.** A
section has many targets (H6.5: 135 signatures across the nine sections), and
PARITY.md's envelope gives one `result` per `input_id`. H6.2 defines an
observation for one target with one tuple of bound inputs, and PARITY.md calls
`result` "the canonical observation" in the singular — both point the same way,
but neither settles whether one record carries one (household, target, bound
arguments) observation or bundles a section's targets into an object keyed by
target. Both are legal wire values and both are lossless, so this is packaging
rather than semantics, and it is builder-owned. It is not, however, free: the
choice defines what counts as one input, and the frozen corpus identity, the
≥ 10k input target, the ≥ 20 hits per oracle arm coverage gate and the kill-rate
denominator are all denominated in that unit. My recommendation, not a
requirement: one record per (household, target, bound-argument tuple), because it
is the granularity H6.2 itself defines an observation at and it keeps coverage
counts directly interpretable. Record the choice in `Interface/` where both lanes
see it, and state it in the Phase 1 report so Dev can object cheaply while the
corpus is still unfrozen.

**What remains genuinely unresolved and is not a codec question:** the
envelope-defect classification from A-005 item 6 and A-007 §3(f) — whether a
missing `result` key is exit 2 or a mismatch — which Dev explicitly left open.
That is the meter's behaviour, not the producers'; it does not block Phase 1
production, and no producer should be built to depend on either reading.

## Rationale

Both halves of this question turn on one distinction: code that fails to
implement a signed decision versus a decision that has not been made. An encoder
emitting non-JSON is the first — H6.2 already said JSON, and the only reason the
bug exists is a docstring assumption about a corpus that is not the population
the encoder serves. A wire spelling is also the first once the shape it spells is
signed, because a lossless codec of an approved structure adds no claim anyone
could disagree with. What is genuinely the second kind is narrow and I have kept
it narrow: one sentence in PARITY.md that still blocks producers by its own
stale terms, and one packaging choice whose consequence is arithmetic rather than
meaning.

The part worth insisting on is the byte-pinning. `observe` sorts on the encoded
string, so escaping and formatting are not cosmetic: they determine array order,
and array order is compared. Two isolated lanes cannot converge on those bytes by
reasoning independently from H6.2, which does not specify them. `Interface/` is
the only channel they share, so the bytes have to be written there, now, before
either lane commits to a mirror of the other's guesswork.
