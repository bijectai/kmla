## Answer

### 1. Verdict: implementation defect, already determined by signed text

Dev's interpretation is confirmed. No new owner choice is needed, and the reason
is a precondition rather than an interpretation.

**H4.2(ii)** applies to "every binary **event** predicate with the **event
position** bound to each event". It presupposes two things: that the predicate is
an event predicate, and that it has an event position to bind. **H3**
(`human/DECISIONS.md:645`) gives `country_/2` the roles **(place, country
string)**. There is no event position, so the step-(ii) rule does not reach this
predicate at all. Binding position 1 to each event is not a strict reading of
H4.2 — it is applying a rule whose precondition is unmet, and the observable
consequence is that a ground place string matches no event and the supplied fact
disappears.

Three signed passages then require the fact to be carried:

- **H1**: facts are "in source order after grounding (H4.2), with duplicates
  kept; nothing is keyed, deduplicated, sorted or defaulted. An absent fact is
  simply absent (G5)." A supplied ground fact is a fact.
- **H3**: "Predicates with zero statute reads are still part of `Household` (the
  serializer must round-trip them) but never affect any output." Household
  membership is fixed by H3's declared-predicate list, not by whether step (ii)
  happens to find the clause — and this predicate has four reads, not zero.
- **G5**: "A fact is true iff it occurs in the Household list", which is what
  turns the omission into an observable difference.

So preserving these clauses follows directly from H1/H3, and the event-position
restriction applied to a place is a builder bug. The alternative — that H4.2
needs supplementing — would only arise if H3 gave `country_/2` an event in
position 1, or if the clauses were rule-defined. Neither holds.

### 2. Source and count claims, verified rather than adopted

- Fourteen case files supply exactly one `country_` clause each, and all are

  `s3306_c_B_neg`, `s3306_c_1_pos`, `s3306_c_1_neg`, `s3306_c_1_A_i_pos`,

  `tax_case_51`, `tax_case_81`, `tax_case_82`.
- `s3306_c_A_pos.pl:15` is `country_("baltimore, maryland, usa","usa").` as

On Dev's caution against generalising over H3: I checked the table rather than
asserting a rule. Of every binary predicate listed, **`country_/2` is the only
one whose declared position-1 role is not an event**. `first_day_year/2`,
`is_before/2` and `last_day_year/2` are statute predicates with zero case
clauses, so they are never supplied; `patient/2` — the underscore-less, inert
one — has two clauses at `tax_case_25.pl:11-12`, and both carry an event
(`bob_birth`) in position 1, so they are unaffected. Scoping the fix to
`country_` by name is therefore not merely the conservative choice; on this
corpus it is also a complete one. That is a measured statement about H3's table
today, not a design rule about predicates.

### 3. The mismatch mechanism, with one refinement to the framing

The question attributes the change to the NAF sites at `:468` and `:483`. The
truth values there do change, but the **solution loss comes through the positive
read at `:464`**. `section3306.pl:462-471`:

```prolog
( ( country_(Geographical_location,Country), Country=="usa" )
; ( \+ country_(Geographical_location,_), Geographical_location=="usa" ) ).
```

With the fact, the first disjunct binds `Country="usa"` and succeeds, so
`s3306_c_A(alice_employer,Employer,Employee)` yields
`[[{"a":"alice"},{"a":"bob"}]]`. Without it, the first disjunct fails; the second
reaches its NAF, which now succeeds under G5, and is then defeated by
`Geographical_location=="usa"`, since the location is
`"baltimore, maryland, usa"`. Result `[]`. The NAF is not what removes the
solutions — it is reached and then loses on the string comparison.

This matters for the regression, because the mirror site has the opposite sign:
in `s3306_c_B` (`:479/:483`) the same omission makes `\+ country_(Location,_)`
succeed and `Location\=="usa"` succeed, so dropping the fact can **add**
solutions there. A regression that only looks for lost solutions would miss that
direction, and `s3306_c_B_pos`/`_neg` are among the 14.

### 4. What the failure says about the verification design

H4.3(a) passed while (b) failed, and that is worth recording rather than treating
as incidental. **(a) is a fixed-point check**: a grounder that drops the same
facts on every pass satisfies it. So (a) can never detect a consistently lossy
grounder, and this finding is the demonstration.

(b) catches losses only where a queried goal can observe them. It therefore
cannot catch a dropped fact for a predicate with zero statute reads — precisely
the predicates H3 explicitly still requires to round-trip. Neither H4.3 check
covers that class, so the regression needs a **direct comparison of supplied
clauses against the emitted fact list**, independent of both. No such predicate
is currently mis-handled, since `patient/2`'s clauses carry an event; the point is
that if one were, nothing in H4.3 would say so.

### 5. Scope and regression

Dev's scoping is right and I would not widen it. Carrying `country_/2` clauses as
supplied — source order, tags, multiplicity, deterministic placement recorded so
H4.3(a) holds — follows from H1/H3. Scoping by name, rather than by "bodyless
event facts" or by "predicates with no event position", avoids asserting a general
rule the text does not state, and §2 shows the narrow scope loses nothing today.
A rule-defined `country_` clause is not covered, is absent from the corpus, and
the handling should fail closed if one ever appears.

Required regression, as Dev states it plus two additions from §3 and §4: all 14
files; both H4.3 checks for each; the original
`[[{"a":"alice"},{"a":"bob"}]]` observation restored in `s3306_c_A_pos`; the
opposite-sign check on `s3306_c_B_pos`/`_neg`; and a direct supplied-clause to
fact-list comparison. The failing diagnostic stays failing until the fix passes
it.

Explicitly not authorized by any of this: bypassing step (ii) for bodyless event
facts in general, deduplicating the outer event traversal, widening the
`tax_case_33` domain, or changing any comparison or canonicalization to make the
mismatch disappear. And I agree with the question's framing that this finding
lives in the generic event-domain traversal and is not evidence that the scoped
`tax_case_33` exception needs a different service domain; that candidate's
measured H4.3(a,b) result stands on its own.

## Rationale

The classification turns on one word in H4.2(ii) — "event" — appearing twice, as
a qualifier on the predicate and again on the position. A grounder that treats
"binary predicate declared in `events.pl`" as equivalent to "binary event
predicate with an event in position 1" will handle every case in the corpus
correctly except this one, which is exactly the shape of bug that survives
testing: the misreading is invisible until a predicate whose first argument is a
place turns up, and there is only one.

The part worth carrying forward beyond this fix is §4. H4.3(a) passing here is
not a near miss; it is the check behaving as specified, since re-grounding an
incomplete Household reproduces the same incomplete Household. Preservation
checks that compare a system against its own output cannot detect uniform loss,
and the corpus contains predicates that H3 requires to round-trip while no
observation can see them. That gap is structural, not a property of this bug.
