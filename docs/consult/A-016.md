# A-016

Lean proof-engineering answer. No approved semantics change, no assertion is
weakened, no axiom or native evaluation is involved, `human/` is untouched, and
nothing here needs Dev.

## Answer

### 1. What the error message means

"Tactic `decide` failed … because its `Decidable` instance did not reduce to
`isTrue` or `isFalse`" is **not** a claim that the proposition is false or that a
bound is wrong. It says `whnf` got stuck on a term it cannot unfold. The value is
not in question: your executable guards already compute `false` for this query,
and `#eval` runs compiled code while `decide` runs definitional unfolding. A gap
between the two is always a reducibility problem, never a semantics problem.

This also explains why all three prior edits failed identically, including
`decide +kernel`. `+kernel` changes *who* does the reduction, not *what can be
unfolded*; a definition that blocks in the elaborator for this reason blocks in
the kernel for the same reason. A fourth variation on the tactic cannot succeed.

### 2. The blockers, by name

The goal is `emptyH.v3ForQuery 2015 (r8 (day "2101-01-01")) = false`, and
`v3ForQuery h y q = h.v3 y && q.v3` (`Interface/QueryTime.lean:135-136`). The
household half is cheap. The query half reaches
`Pat.dayWellFormed (.val (.str "2101-01-01"))` =
`(Day.fromISO? "2101-01-01").isSome` (`Interface/Household.lean:690-693`), and
`Day.fromISO?` (`Interface/Household.lean:662-677`) opens with

```lean
let [ys, ms, ds] := s.splitOn "-" | none
let y ← ys.toInt?
```

Both are core `String` functions defined by well-founded recursion over
`String.Pos` — `String.splitOnAux` and, under `toInt?`, `String.toNat?` →
`String.isNat` → `String.anyAux`. A WF definition elaborates to
`WellFounded.fix`, whose `Acc.rec` only reduces when the accessibility argument
is in constructor form. It never is: it comes from a theorem. So the instance
gets stuck precisely there. (If your toolchain still has `splitOnAux` as
`partial`, it is worse — an opaque constant that cannot reduce at all.)

A second blocker sits one line later for any *positive* guard, though not for
this one: line 677's round-trip `Day.toISO day == s` calls `toString n.natAbs`
(`Household.lean:617`), i.e. `Nat.repr` → `Nat.toDigits`, also WF. This
particular assertion never reaches it — the year 2101 fails the `y ≤ 2100` test
at line 667 and returns `none` first — but every guard asserting that a *good*
date is accepted will stall there, so both sides need fixing.

`String.pushn` (also in `toISO`) is structural on `Nat` and is fine;
`queryTimeSchema?`'s literal-pattern match and `Int` comparisons on literals are
fine.

### 3. A bounded diagnosis, without touching the assertion

Six one-liners in a scratch file. Each is a `by decide`; record pass/fail. This
is the diagnostic isolation you are already doing, narrowed to the smallest
terms that discriminate the causes, and it does not count as an edit cycle on the
guard.

```lean
example : "abc".data = ['a','b','c'] := by decide              -- 1 literal expansion
example : ("2101-01-01".splitOn "-").length = 3 := by decide    -- 2 expect FAIL
example : "2101".toInt? = some 2101 := by decide                -- 3 expect FAIL
example : queryTimeSchema? "s3306_c_10_A_ii" 3 |>.isSome = true := by decide  -- 4
example : Day.toISO 0 = "1970-01-01" := by decide               -- 5 expect FAIL
example : emptyH.v3 2015 = true := by decide                    -- 6 expect pass
```

Rung 1 checks the one assumption everything else rests on: that the kernel
expands a `String` literal to constructor form when a projection demands it. If
1 fails, no string-valued definition will ever reduce and the plumbing must take
`List Char` at the boundary. If 1 passes and 2 and 3 fail, the diagnosis in §2 is
confirmed and the fix below is exactly sufficient. Rung 4 isolates the generated
table independently of the date parser, so a failure there is a separate defect
and not confused with this one.

### 4. The fix: kernel-reducible shared plumbing

Replace the core `String` calls on the `decide` path with structurally recursive
equivalents in `Interface/`. Structural recursion compiles to `List.rec`/`Nat.rec`
and reduces in the kernel; this is the pattern the project already prescribes
over `partial`.

```lean
private def splitOnCharAux : List Char → Char → List Char → List (List Char)
  | [],      _,   acc => [acc.reverse]
  | c :: cs, sep, acc =>
      if c == sep then acc.reverse :: splitOnCharAux cs sep []
      else splitOnCharAux cs sep (c :: acc)

def splitOnChar (s : List Char) (sep : Char) : List (List Char) :=
  splitOnCharAux s sep []

private def digitsToNat? : List Char → Option Nat
  | []      => none
  | c :: cs =>
      cs.foldl (init := digitOf? c) fun acc ch =>
        match acc, digitOf? ch with
        | some n, some d => some (n * 10 + d)
        | _,      _      => none
```

with `digitOf? c := if '0' ≤ c && c ≤ '9' then some (c.toNat - '0'.toNat) else none`.
`Char` comparison goes through `UInt32`/`Fin`/`Nat`, all of which reduce, and
`Nat` literal arithmetic has kernel acceleration. Then `Day.fromISO?` matches on
`splitOnChar s.data '-'` with the same three-component pattern, the same bounds
at line 667, the same civil-date arithmetic, and the same round-trip test — with
`Day.toISO`'s digit rendering likewise replaced by a structural
`natToDigits (fuel : Nat)` rather than `toString`.

**What must be preserved, and how to know it was.** D2 and A-015 pin the accepted
language exactly: `"1900-02-29"`, `"2017-02-30"` and `"2017-1-1"` are rejected,
not repaired, and an integer in a day slot is malformed. The rewrite must not
move that boundary by accident — a hand-written digit scanner could, for
instance, start accepting a leading `+`, unicode digits, or an empty component.
Pin it with `decide` guards over a small table the moment the plumbing is
structural, including those three strings, `""`, `"2015-01-01-01"`, `"2015-01"`,
`"+2015-01-01"` and one valid date. Those guards are cheap once reduction works,
and they are what makes "no semantics changed" a checked claim rather than an
assertion.

`toISO` is the half that must stay in step: since line 677 tests
`Day.toISO day == s`, the parser and the renderer jointly define the accepted
language, so change them together and keep the same equality test.

### 5. Then remove the fragility permanently

Once reduction works, prove the characterization instead of relying on evaluation
for every future guard:

```lean
theorem Day.fromISO?_eq_some {s : String} {d : Day} :
    Day.fromISO? s = some d ↔ Day.inRange d ∧ Day.toISO d = s
```

The forward direction is nearly definitional — line 677 already checks both
conjuncts before returning `some`. The reverse needs only that `toISO` emits
three `-`-separated digit groups in range, which the structural renderer makes
provable. With that lemma, later guards are discharged by rewriting rather than
by unfolding a parser, which is both faster and immune to the next core-library
change to `String`.

### 6. Routes ruled out

- `native_decide` — the hygiene gate makes it INVALID, and it would replace a
  kernel proof with a compiler run, which is the one thing this benchmark is
  built to refuse.
- Restating the claim on an already-decoded `Day` instead of the string. This is
  the tempting shortcut and Q-016 is right to forbid it: the assertion would
  change from "this spelling is rejected" to "this day count is rejected", which
  is a different proposition and not the one that closes V3's supplied-date gap.
  Acceptable only as a corollary of §5's lemma, never as a replacement for the
  guard.
- Weakening to `≠ true`, adding an axiom, or marking the guard `sorry`-ed and
  reporting it as unproved — unnecessary here, since the obstruction is
  mechanical and has a known fix.
- `simp` with equation lemmas for the WF definitions is a legitimate fallback if
  §4 somehow stalls, but expect `String.Pos` arithmetic to defeat it; I would not
  spend a cycle there before trying §4.

### 7. Circuit breaker

The prior stop was correct and the diagnosis in §2 is what it bought. For
accounting: §3 is diagnosis in scratch files and is not a cycle on the guard;
§4 is one cycle, which should either close the goal or produce a *different*
error message. If it produces the same "did not reduce" message with the
structural plumbing in place, stop again and report — that would mean rung 1
failed, or that a blocker exists I have not identified, and a third variation
would be guessing.

## Rationale

The useful move here is separating a reducibility obstruction from a semantic
one, because they present identically at the tactic level and the remedies point
in opposite directions. Treating this as a semantic problem leads to adjusting
the date bound or restating the claim until `decide` succeeds — which would
produce a green guard that no longer guards the thing Dev asked to be closed.
Treating it as a plumbing problem costs one rewrite of two helper functions and
leaves the assertion exactly as written.

The reason to go further and prove §5's characterization is that this will
recur. Every supplied-date check in the V3 extension, and every future guard over
the enumerated day positions from A-015, lands on the same parser. Proving its
specification once converts an open-ended sequence of evaluation-dependent proofs
into rewriting against a lemma, and makes the accepted language a stated theorem
rather than a property of whichever `String` implementation core ships.

None. The assertion, the V3 bounds, D2's accepted-and-rejected date language and
every approved semantics are unchanged; only the implementation of two helpers
moves, under a unit-guard table that pins the language it implements.

## Escalate to Dev

No. This is builder-owned `Interface/` plumbing and a Lean proof technique. The

accepted — which is precisely what the §4 guard table exists to prevent, and if
one of those guards cannot be made to hold, that is the moment to stop and
escalate rather than adjust it.
