## Answer

### 1. The finding, restated as the evidence now shows it

Dev's objection was right and is now answered. H4.2 step (ii) binds the event
position, and the diagnostic runs the original goal unchanged,
`findall(Purpose,purpose_(payment_2015_1,Purpose),Purposes)`, with
`Payment_event` the ground atom `payment_2015_1`. The **first**
`split_string/4` accepts it and binds `Xp="payment"`, `Yp="2015"`, `Zp="1"`. The
**second**, on the free `Service_event`, raises. So the raise is not an artefact
of calling with the event unbound; H4.2's prescribed mode is satisfied and the
clause is still not groundable, because it needs a second input the procedure
never supplies. That is exactly the condition Dev set for entertaining an
amendment, and P-GROUND2's body should be read through this sharper statement.

### 2. Verdict

**Endorsed as a sufficiently explicit candidate to implement and verify**, with
four clarifications in §3 that change no domain, no order and no promise. I found
no missing owner choice and no counterexample to this `tax_case_33`-scoped
candidate.

What makes it explicit, concretely:

- **Scope is pinned, not described.** One rule, one file, one SHA-256. An
  exception that can only be identified by a digest cannot silently generalize,
  which is the failure mode a "binary predicates that need two inputs" rule would
  have had.
- **The second-input domain is stated and justified by the clause itself**, not
  inferred: the body requires `Xs=="workforalice"`, and in this file every
  `workforalice_*` term is declared by `service_/1`. No other unary event
  predicate in the case produces one, so the `service_/1` projection covers every
  *declared* term that can satisfy the test.
- **The traversal order is fully determined**: events in step (ii)'s order,
  then distinct `service_/1` terms in first-occurrence order, then proofs in
  interpreter order. Three nested loops, no free choice left to the implementer.
- **Multiplicity is handled explicitly in both directions**: the domain is
  deduplicated, the proof results never are.
- **The promise is H4.3, stated as unmeasured.** The draft says outright that it
  does not claim preservation, does not claim global extensional completeness,
  and has not measured either H4.3 check or the cost. That is the right promise
  and the right epistemic status.

One property worth naming because it is not obvious and it matters: **the chosen
order is stable under re-grounding**, which H4.3(a) needs. The second grounding
sees ground `purpose_` facts, so step (ii) with position 1 bound collects, for
each event, exactly that event's facts in clause order — which is the first
grounding's nested order restricted to that event. The nested loop and the
re-grounding loop therefore produce the same sequence. A different inner order,
say sorting the services, would have broken this.

### 3. Four clarifications to fold into the draft before implementation

None of these is an owner choice; each is a place an implementer would otherwise
decide silently.

**3.1 Replacement, not supplement.** "Step (ii) binds both inputs. Keep the
first-position event traversal from step (ii)" can be read as *also* running the
ordinary single-input call, which is the call that raises. Say explicitly that
for this predicate in this file the two-input call **replaces** the single-input
call of step (ii), so the raising call is never made and the predicate is not
traversed twice.

**3.2 Step (i) must retain per-predicate provenance.** H4.2 step (i) is worded as
producing "the event universe" — a union. The candidate consumes the `service_/1`
projection of it, not the union. The grounder therefore has to keep which unary
predicate produced each term. This is an existing interface detail of step (i)
rather than a change to it, but nothing currently says so.

**3.3 The dedup asymmetry is deliberate.** The inner domain is traversed "once
per distinct tagged term"; the outer event traversal is inherited from step (ii)
and is *not* deduplicated, so a term declared twice by unary predicates yields two
outer iterations. Both choices are defensible and the draft makes only one of
them visible. Saying that the asymmetry is intended stops an implementer from
"tidying" it in either direction.

**3.4 Key the exception so it fails closed.** The scope is owner-set and correct;
how the grounder *recognises* the rule at run time is the builder's, since clause
line numbers need not survive the reader. Whatever key is used — file digest plus
predicate indicator plus clause position, or the clause term compared against a
stored copy — it must halt and report if it does not match **exactly one** clause
in the file of that digest. Failing closed is what keeps an implementation detail
from widening an owner-scoped exception.

### 4. Two notes for the verification report, not for the text

**4.1 H4.3(b) is order-insensitive.** It compares canonical solution sets, so it
cannot detect a fact-ordering change that alters a *first-solution* observation.
That matters only for scalar entry points under H6.1, and for this case H6.1
already records that `tax/3` always has exactly one solution, so the exposure is
nil here. Worth one line in the report rather than silence, because the general
claim "H4.3 passed" is weaker than "ordering is preserved".

**4.2 A-019's place-purpose observation is not evidence against this candidate,
and I am not offering it as such.** `section7703.pl:146-153` can bind
`purpose_/2` position 2 to a place, but the clause requires `Xs=="workforalice"`,
and a place or a literal string fails that test — `split_string` on a term with
no `"_"` yields a one-element list and the `[Xs,Ys,Zs]` pattern fails rather than
raising. The observation bears on a *general* domain rule, which this draft
explicitly does not propose. H4.3 is the criterion; running it is what settles
this case.

### 5. What endorsement does not cover

Implementing and measuring, per Dev's conditional authorization. It does not
certify preservation, does not authorize any fallback on a raise or a failed
check, does not permit skipping an original or widening the domain, does not
touch comparison or canonicalization, and does not bear on Checkpoint 1. If
verification fails, the result is a finding and a fresh question, not a
broadened candidate.

## Rationale

The draft is narrow in exactly the way that makes a candidate testable: it names
one rule by digest, states a domain, fixes an order, declares what it does not
promise, and hands the whole preservation question to H4.3 rather than to a
completeness claim it cannot support. That is a better shape than the general
procedure P-GROUND2's body contemplated, because a general procedure would have
required a completeness argument over a relation that A-019 showed to be
infinite, while this one requires a measurement over 376 files.

The four clarifications are all of the same kind, and it is worth saying why they
are worth raising at all given that none changes the proposal: each is a point
where the text is silent and an implementer must act anyway. Silence plus
necessity is how an unowned decision gets made by whoever types first — which is
the pattern behind most of what this consult channel has had to correct, from the
enumeration-scoped V3 check to the list-valued eligibility provider.
