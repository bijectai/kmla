## Answer

### 0. A-016's blanket claim was too strong

A-016 §2 said every well-founded core `String`/`Nat` definition is irreducible in
the kernel. That is wrong as a blanket rule, and your diagnostic shows why: a WF
definition can reduce — the equation compiler's unfolding does fire in many
cases — it is just expensive. `#reduce escapeJson "b"` hitting the *default
recursion limit* is the tell. A term that is blocked on an opaque constant stops
immediately; a term that exhausts `maxRecDepth` was unfolding the whole time.
Treat A-016's §2 as "WF definitions *may* block, and are in any case costly", and
its §4 structural rewrite as a way to make evaluation cheap rather than a
prerequisite for it.

Corroboration from your own file: `a1_admission_checks_actual_year` and
`b3_admission_checks_actual_year` (`Oracle/Tests/S7703.lean:245-246`) are among
the 50 that elaborate, and those are exactly `decide` through `QueryCall.v3` →
`Pat.dayWellFormed` → `Day.fromISO?` → string parsing. The machinery that
defeated Q-016 now reduces. So the remaining three failures are about term size
and tactic choice, not about reducibility in principle.

### 1. Test 1 is true, and the residual is `X ++ [] = X`

The printed goal is provable as stated; nothing about the certificate,
multiplicity or the arbitrary continuation needs to move. The arithmetic:

- `min 16618 16800 = 16618`
- `16618 - 16436 = 182`
- `2 * 182 = 364`
- `364 ≤ 364` holds, so the `ite` takes the `then` branch and the scrutinee list
  is `[()]`.

Then `List.flatMap f [()]` unfolds to `f () ++ []`, and `f () = X` where
`X = (dependency bob alice 2015 checked).flatMap (fun _ => [(home, bob)])` is
opaque. So the whole residual is `X ++ [] = X` — `List.append_nil`, not anything
semantic.

Why `simp` stopped there: core's literal simprocs cover `Int` `≤`, `*` and `-`,
but `min` on `Int` is `Min.min`, which no simproc evaluates, so
`min 16618 16800` survived, the condition never became `True`, `if_pos` never
fired, and the scrutinee stayed symbolic — at which point `List.flatMap` has
nothing to reduce and `List.append_nil` never gets a chance.

This also confirms the statement against the signed semantics rather than merely
against itself: 16436 is 2015-01-01, 16618 is 2015-07-02, 16800 is 2015-12-31,
and D4's table says in so many words that "a residence from Jan 1 to Jul 1 is 181
days and fails in a common year; Jan 1 to Jul 2 passes", with the common-year
threshold 364. The test is `childHome (jul1 + 1)`, i.e. Jul 2, and the goal's
arithmetic lands exactly on the documented boundary. There is no semantic
question here to resolve.

**Proof plan**, leaving the existing `simp` set untouched and adding one step:

```lean
  have hguard : (364 : Int) ≤ 2 * (min 16618 16800 - 16436) := by decide
  simp [hguard, /- existing lemma list unchanged -/]
```

`decide` closes `hguard` because `Min Int` unfolds to `if a ≤ b then a else b`
and `Int.decLe` reduces on literals. `simp [hguard]` rewrites the condition to
`True`, `if_pos` fires, `List.flatMap_cons`/`List.flatMap_nil` reduce the
singleton, and `List.append_nil` closes the goal with `X` still opaque — which is
the point of the test. Two equivalent spellings if the `have` does not rewrite
where you want it: `rw [if_pos hguard]` before the `simp`, or adding
`Int.min_def` to the existing simp set so the simprocs can finish the arithmetic
themselves. I would try the `have` first; it makes the boundary value explicit in
the proof text, which is worth something in a test whose name is about the exact
duration.

### 2. Tests 2 and 3: `decide` is the wrong tactic for a `String` equation

Both goals are `List String` equalities against string literals. `decide` on such
a goal must reduce `instDecidableEqList` → `String.decEq` → a `List Char`
comparison where every `Char` is a structure carrying a `UInt32` and a validity
proof, and it must drive that all the way to `isTrue`/`isFalse`. `rfl` compares
the two sides by kernel defeq, where string literals are compared directly. For
goals of the shape `<computation> = "literal"`, `rfl` is both the cheaper and the
more likely-to-succeed tactic, and that asymmetry is very probably the whole
story here.

Second, the `simp only` list in both proofs unfolds `escapeJson` and rewrites
`String.foldl_eq_foldl_toList` *before* the final step. That trades a closed,
evaluable call for an open `List.foldl` over `String.toList`, which then has to be
re-evaluated through `String.mk`/`List.append` by whatever tactic follows. It is
working against the kernel's literal handling rather than with it. The cleaner
shape is: rewrite the oracle-side facts (`a1_absent_start_and_end`,
`b3_marriage_multiplicity`), `simp only` the *oracle* definitions to make the
argument of `observe` concrete, and then close with `rfl` without unfolding any
string machinery at all.

Third, and this is the one lever you have not pulled: resource limits.
`set_option maxRecDepth 100000` and, if elaboration times out rather than
recursing, `set_option maxHeartbeats 1000000`. `#reduce escapeJson "b"` hitting
the *default* limit is direct evidence that 512 is simply too small for
`String.foldl`'s unfolding, and both options are resource bounds, not
check-disabling switches — they change nothing about what the kernel verifies.
One flag rather than an assumption: confirm that the hygiene gate's
"check-disabling `set_option`" rule classifies `maxRecDepth`/`maxHeartbeats` as
resource limits, and whether `Oracle/Tests/` is inside the gate's scope at all.
If the gate would reject them, say so and the plan changes to §5's structural
route instead.

### 4. Bounded diagnosis, read-only

A scratch file, not edits to the test. One `set_option maxRecDepth 100000` at the
top, then each rung twice — once `by rfl`, once `by decide` — recording which
succeeds:

```lean
#eval observe (a1Solutions (s7703_a_1_bfffb (hh married) alice y))   -- rung 0
example : escapeJson "bob" = "bob" := by rfl
example : Obs.encode (.atom "bob") = "{\"a\":\"bob\"}" := by rfl
example : Solution.encode [.atom "bob", .atom "marriage", .null]
    = "[{\"a\":\"bob\"},{\"a\":\"marriage\"},null]" := by rfl
example : observe [[.atom "bob"]] = ["[{\"a\":\"bob\"}]"] := by rfl
example : observe [[.atom "bob"], [.atom "bob"]] = ["[{\"a\":\"bob\"}]"] := by rfl
```

Rung 0 is the highest-value step and costs nothing: if `#eval` prints exactly the
expected literal, the statement is true and only the proof is at issue; if it
prints something else, you have found a real defect and the next move is a
finding, not a proof. The `rfl`/`decide` pairing at each rung measures the
asymmetry in §2 directly. The last two rungs isolate `mergeSort` and the dedup
`foldr` from the encoder, which matters because test 3 is the one with
multiplicity two.

Interpretation: the first rung where both spellings fail names the culprit. If a
rung fails with "maximum recursion depth" it is cost, and the remedy is §2's
limits plus `rfl`. If it fails with "did not reduce to `isTrue` or `isFalse`"
*under a raised limit and with `rfl` also failing*, that is a genuinely stuck
term, and A-016 §4's structural replacement of the offending helper — inside
`Interface/`, with a unit-guard table pinning the accepted language — becomes the
right fix rather than a speculative one. That is a fourth cycle's worth of work
and needs Dev's go-ahead, since it touches shared plumbing.

## Rationale

Three tests failing at once looks like a shared cause, and there is one — but it
is the proof strategy, not the implementation. Both string tests reach for
`decide` on a `String` equality, which is the most expensive way to ask the
kernel that question, and both pre-unfold the encoder into a shape the kernel can
no longer shortcut. Test 1 is unrelated to those two and stops for a third
reason, a missing literal reduction for `min` on `Int`; its residual is a
one-lemma goal.

The reason to run rung 0 before anything else is that it separates the only two
possibilities that matter. If the evaluated observation differs from the expected
literal, no amount of tactic work is appropriate and the right output is a
finding against the encoder. If it matches, every remaining question is about how
to persuade the kernel of something already known to be true, and that is
bounded work with a known ladder.
