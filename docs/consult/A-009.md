### 1. Where R5 is wrong

R5 (`human/DECISIONS.md:1363-1367`) asserts that each round trip of the group
"moves from a taxpayer to a child living with them (`s7703_b_1` requires
`s152_a_1(Dependent,Taxp)`), so the recursion follows the child relation and
terminates under V4". Two independent errors, either of which is sufficient:

1. **`s152_c_2` is a disjunction and R5 read only one disjunct.**
   `section152.pl:158-160` offers `s152_c_2_A` *or* `s152_c_2_B`. R5's "follows
   the child relation" is true of (c)(2)(A) alone. (c)(2)(B)
   (`section152.pl:178-187`) admits "a brother, sister, stepbrother, or
   stepsister", and both admitting predicates are **symmetric**:
   `is_sibling_of/4` (`utils.pl:131-156`) accepts `X` and `Y` in either the
   `agent_` or the `patient_` position of the same `brother_`/`sister_` event,
   and `is_stepsibling_of/4` (`utils.pl:167-187`) is symmetric in `X` and `Y` by
   construction. A symmetric relation is a 2-cycle by definition.
2. **V4 does not reach these edges.** V4 constrains the directed graph built from
   `son_`/`daughter_`/`father_`/`mother_` events. A `brother_` event contributes
   no edge to it. The fixture's V4 graph is empty and therefore acyclic, while
   the relationship the recursion actually follows is a cycle.

A third condition would have saved R5 if the source read the way the statute
text does. §152(c)(3) requires the dependent to be "younger than the taxpayer",
which is antisymmetric and would break the cycle at depth one. But
`section152.pl:204` discharges it with `is_before(Taxpayer_dob,Individual_dob)`,
and `is_before` is `Stamp1 =< Stamp2` (`utils.pl:10-14`). With equal birth dates
each of the two is "younger than" the other. Note this is not a divergence
between code and evident intent that the oracle may quietly repair: under
P-INTENT clause 2 the oracle translates the code as written, and a strict
`is_before` could not reach parity with the pinned program.

### 2. No signed condition rejects the input

I walked H5 against the fixture and found nothing that excludes it:

- **V1** — `brother_/1` is declared (`events.pl:11`), as are `birth_`,
  `marriage_`, `residence_`, `agent_`, `patient_`, `start_`; argument kinds match
  H2; no wildcard; no stipulations; every string non-empty. Satisfied.
- **V2** — no `amount_` facts; vacuous. **V3/V9** — all days in 1900–2100,
  zero-padded ISO, year 2018 in range. Satisfied.
- **V4** — no `son_`/`daughter_`/`father_`/`mother_` events, so the graph is
  empty and acyclic. Satisfied, and this is precisely the point: the rule that
  was supposed to bound this recursion is satisfied *because* the input uses a
  relation the rule does not mention.
- **V5, V6, V7** — no `service_`, `plan_` or `payment_` facts, so E1, E2 and the
  E4 domestic cycle are structurally unreachable. Satisfied.
- **V8** — `hohCycle` requires `y ∉ [2018,2025]`; `y = 2018`, so the conjunction
  is false and `¬ hohCycle` holds. Satisfied.

Nor does any conjunct on the path prune the recursion. I traced it against the
source: `s7703_a_1` succeeds on each ongoing marriage with no death and no end
(`section7703.pl:17-37`); `s7703_b_1`'s joint-return NAF succeeds vacuously
because there are no `joint_return_` facts, the shared `home` supplies both
`residence_` conjuncts, and the unbounded residence gives a full-year duration
(`section7703.pl:110-139`); `s152_c_1_B` likewise overlaps for the whole year
(`section152.pl:89-136`); `s152_c_3` is satisfied in both directions by the
equal-date `is_before` and the under-25 check (`section152.pl:192-230`); and
`s152_c_1_E` (`section152.pl:143-153`) calls `s7703(Dependent,Spouse,_,Taxy)` as
the **first** conjunct inside its NAF, so the absence of joint-return facts —
which would make the conjunction fail — is never reached, because evaluation
diverges before the later conjuncts are tried. That ordering is the load-bearing
detail: a reader who assumes "no joint returns, so (c)(1)(E) is trivially true"
will not see the cycle.

So the answer to "identify any missed signed condition or source conjunct that
would reject the input" is: there is none. If Dev finds one I would want to see
it, because I looked for one specifically.

### 3. What the evidence does and does not establish

Three distinct levels, kept apart as Q-009 asks:

- **The runtime results are bounded-budget evidence.**
  `inference_limit_exceeded` at 10⁵ and 10⁶ inferences shows only that no answer
  was produced within those budgets. It is consistent with divergence and with a
  merely very slow but finite search. By itself it proves neither. It is also
  emphatically not a parity result or an empty answer: PARITY.md and
  `docs/contracts/RUNTIME.md` classify a timeout as an infrastructure failure, so
  such an input can never yield a comparison, only a failed run.
- **The structural argument is a sound informal proof of divergence, not a
  machine-checked one.** The goal `s7703(a,sa,_,2018)` recurs with identical
  arguments after a finite derivation, in a pure SLD derivation with no tabling,
  no assert/retract on the path, and no cut between the recurrence and its
  origin; the database is unchanged between the two occurrences, so the same
  subtree is entered again, unboundedly. I regard that as conclusive for the
  Prolog side at the level of rigour this project uses elsewhere, and I am
  labelling it an argument rather than a proof. The `no_sibling_control` run,
  which terminates once `brother_` is retracted in a fresh diagnostic process,
  corroborates that the sibling edge is the driver.
- **"The fixture is `Valid`" is a specification-level deduction, not a
  certificate.** The production V7/V8 `OracleGuards` do not exist, so nothing is
  kernel-checked. The deduction is unusually safe here because V5–V8 are
  vacuously satisfied for structural reasons (absent fact classes, and a year
  inside `[2018,2025]`) rather than by any computation, but it remains a hand
  check and should be re-run mechanically once the guards exist.

### 5. Recommended conservative formulation, for Dev to review

Recorded as **P-R5CYCLE (PROPOSED)** in `docs/DECISION_LOG.md`. Stated in the
style of V5–V7, decidable, deliberately over-approximating, and — unlike V7 and
V8 — checkable from the fact list alone with no `Oracle/` import:

> **V10 (E6, §152(c)(2)(B) symmetric-relationship cycle).** No two distinct
> persons `p ≠ q` connected in the undirected relationship graph — an edge for
> every `brother_`/`sister_` event linking them, every stepsibling pair under
> `utils.pl:167-187`, and every `is_child_of` edge — have `birth_` events whose
> `start_` days are equal.

**Why equal birth dates are the right thing to exclude.** Around any cycle of
this group each Dependent becomes the next leg's Taxpayer: `s152_a_1(Dep,Taxp)`
recurses to `s7703(Dep,…)` and thence to `s7703_b_1(Dep,home,Dep')` and
`s152_a_1(Dep',Dep)`. Every leg passes through `s152_c_1_C` → `s152_c_3`, because
`s152_c_1` conjoins A, B, C, E in that order (`section152.pl:63-67`) and the
recursion sits in E. So each leg must satisfy (c)(3) by one of its two
disjuncts:

- *First disjunct* — both parties have `birth_` facts and
  `dob(Taxp) ≤ dob(Dep)`. Composed around a cycle this gives
  `dob(p₁) ≤ dob(p₂) ≤ … ≤ dob(p₁)`, hence equality for every member.
- *Second disjunct* — the Dependent has **no** `birth_` fact and is a
  `is_descendent_of` the Taxpayer. If any leg uses it, that Dependent is the next
  leg's Taxpayer and has no `birth_` fact, so the next leg cannot use the first
  disjunct either; by induction every leg on the cycle uses the second disjunct,
  and their descendant edges compose into an `is_child_of` cycle, which V4
  already excludes.

So under V4, every cycle of this group requires all of its members to share one
birth date. V10 excludes that, over-approximating by also excluding
same-birth-date related pairs that happen not to close a cycle — the same
deliberate looseness V7 records for E4. A blunter variant, "no two distinct
persons share a birth date", is easier to state and to check but costs `gen/` the
twin boundary cases, which are interesting precisely at §152(c)(3). I recommend
the graph-restricted form.

**A consequence Dev should decide at the same time: R5's fuel constant needs
re-deriving.** Under V10, along a chain the birth dates strictly increase while
the first disjunct is used (adjacent members are related and distinct, hence have
different dates), and any second-disjunct suffix strictly descends the
V4-acyclic child graph, with no return to the first disjunct once the suffix
starts. Each part is bounded by the number of persons, so the two together are
not obviously bounded by R5's `persons.length + 1`; `2 * persons.length + 2` is
safe under this argument. R8 (`human/DECISIONS.md:1386-1387`) inherits whatever
R5 settles on. I would not want the fuel constant carried over unexamined, since
the argument that justified it is the one that just failed.

## Rationale

The reason this matters beyond one hung process is that R5 is a *signed*
termination argument, and the oracle's totality on `Valid` inputs is what lets
the Lean side be a function at all. A fuel parameter whose exhaustion is
unreachable is a legitimate translation of a recursion; a fuel parameter whose
exhaustion is reachable silently converts divergence into `[]` and makes the
oracle disagree with the reference in a direction no differential test can catch,
because the reference cannot be run to produce the comparison. That is why R9
classifies a counterexample as a design flaw rather than a mismatch, and why the
right output of this consultation is a halt and a proposed V-rule rather than a
fuel number.

The shape of the recommendation follows V5–V8 deliberately. Those rules are
over-approximating, decidable exclusions of regions where the reference is
undefined, and Dev already accepted that shape along with the reasoning that the
over-approximation is a deliberate cost. V10 is the same move applied to a region
that was missed because R5 read one disjunct of a two-disjunct clause.
