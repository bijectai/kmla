# A-006

## Answer

Both corrections are accepted. A-005 stands as written and immutable; A-006
supersedes exactly the two passages named below.

### 1. Five governs

Superseded A-005 wording: "four are genuine unresolved contract choices for Dev"
in the opening paragraph, and "would hand Dev fourteen decisions where four
exist" in the Rationale.

The governing count is **five open questions**, as enumerated in A-005's "Which
questions genuinely remain" section and its escalation: items 8, 9, 10, the
definition of "ambiguous IDs" in 13, and 14. The exact arithmetic over the
fourteen items:

- **Seven wholly already specified**: 1, 3, 4, 5, 7, 11, 12.
- **One already specified in its exit semantics, with an implementation
  residue**: 2 (never reuse a run directory; exit 1 is reserved for completed
  comparisons). Astra's work, not Dev's.
- **Two split items**: 6 — two sub-items already specified as exit 2, one
  sub-item deferred to the pending section result specification in
  `DECISIONS.md`/`Interface/`, which is not a new question; and 13 — the
  substance (case-sensitive comparison, one output per engine per selected ID)
  already specified, with the one-line definition of "ambiguous IDs" open.
- **Four wholly open**: 8, 9, 10, 14.

Four wholly-open items plus one open clause inside item 13 is five open
questions. The "four" was a miscount of items against questions, not a different
classification: no item changes category, nothing moves from "already specified"
to "open", and no checkpoint prerequisite is created. Item 14 remains the only
one that can produce a false Checkpoint 1 pass.

### 2. The platform-only guarantee is withdrawn

Superseded A-005 wording: "The case-insensitive-filesystem variant is a
development-environment hazard, not a contract hazard: the graded runtime is
pinned to `linux/amd64` per `docs/contracts/RUNTIME.md`, where the collision does
not arise."

That claim is wrong and is withdrawn. `docs/contracts/RUNTIME.md` pins the
interpreter version, the OS/architecture platform, an immutable image digest,
and that the source is mounted read-only with writable outputs kept separate. It
says nothing about the case sensitivity of any filesystem, and an OS pin does
not imply one: the `--inputs`, `--prolog-out` and `--lean-out` directories may be
bind mounts, volumes, overlays, or host-backed paths, and a bind mount from a
case-insensitive host volume is case-insensitive inside a `linux/amd64`
container. No contract clause currently constrains this, and nothing has been
tested — the eventual runner's mounts do not exist yet, so the review must not
and does not claim otherwise.

Corrected statement: the case-collision hazard is not excluded by any current
contract, in any environment, and is unverified everywhere. It is a genuine
exposure whose severity is that two intended IDs can collapse to one file, which
shrinks the input population silently rather than raising a mismatch. Detecting
that is available on the producer side, where Astra controls file creation; I am
not stating a requirement, only that the mitigation is not on the meter's side.
This does not change item 13's classification: the "ambiguous IDs" definition
remains open and remains Dev's, and no ID policy is chosen here.

## Rationale

The first passage was an arithmetic slip against my own enumeration; the
governing text must be the one that lists the items, since that is what Dev acts
on. The second was a real error of kind: I let a platform pin stand in for a
filesystem property it does not entail, in a review whose purpose is to separate
what the contracts actually guarantee from what the tooling has actually shown.
An unearned guarantee in a review record is worse than an open item, because an
open item gets pinned and a guarantee gets relied on.
