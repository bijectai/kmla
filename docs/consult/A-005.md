# A-005

## Answer

Of the fourteen items in `scripts/parity_conformance.py --list-gaps`, nine are
already fixed by the written text of `docs/contracts/PARITY.md`, one is an
implementation/integration obligation on top of already-fixed exit semantics,
four are genuine unresolved contract choices for Dev, and one sub-item is
deferred to an artifact already pending at Checkpoint 0. None of them is a new
checkpoint requirement, and none of them blocks any Astra lane today. The owner
meter does not exist; I did not inspect any meter source or the exploit corpus.

### Classification, item by item

**1. `mismatches.jsonl` location — already specified.**
Governing wording: "write `mismatches.jsonl` in the invocation's working
directory", plus "The harness invokes the meter in a dedicated run directory and
retains its exit status, diagnostics, input identity, and mismatch artifact."
The harness's `cwd`-per-case behaviour is the contract, not a workaround. The
trailing suggestion "consider pinning an explicit output path instead" is a
proposed contract change; it is not needed and I am not proposing it.

**2. A crashed meter indistinguishable from a completed one — exit semantics
already specified; the residue is implementation.** See the separate crash /
malformed discussion below.

**3. Input record `section` versus `--section` — already specified as
selection, not exit 2.** Governing wording: "Use `--inputs` as the authority for
all input IDs *in the requested section*", "Empty *selected* input populations
fail with exit 2", and "the independent meter only needs the input identity and
section to determine the expected output population." The contract selects by
section; an off-section input record is outside the selected population. The
practical exposure is nil either way, because Astra emits per-section input
directories.

**4. What `prolog` and `lean` hold in a mismatch record — already specified.**
Governing wording: "the missing side is `null` in the mismatch record, and an
existing side contains its full output object." That clause states what a
present side contains; it is not restricted to the missing-output case. Full
output object on each present side, `null` on an absent one. The conformance
harness checks only that the three keys exist, which is correct and stays valid
under either reading; it should not be tightened.

**5. Definition of input-ID order — already specified by the ID grammar.**
IDs match `[A-Za-z0-9][A-Za-z0-9_-]*`, which is pure ASCII, so byte order and
codepoint order coincide. Locale collation is the only way to diverge and the
contract nowhere introduces a locale. Nothing to pin.

**6. Classification of envelope defects — two already specified, one deferred.**
- Missing `result` key: already specified as exit 2. Governing wording: "Each
  engine output contains *exactly* the following fields", plus "malformed
  records fail with exit 2". The comparison clause "absent keys are not null
  values" governs structure *inside* a `result` value, not the envelope. The
  `absent-key-is-not-null` fixture applies that clause at the wrong level: it
  deletes an envelope field. To exercise the clause it cites, the fixture should
  put the absent-versus-null distinction inside the `result` object.
- ID violating the published grammar: already specified as exit 2, same two
  clauses.
- Raw JSON float where a tagged representation is required: deferred, not a new
  question. "Do not coerce numbers" already fixes `1 ≠ 1.0` as a mismatch;
  whether a bare float is a legal wire value at all is settled by the approved
  section result specification in `DECISIONS.md`/`Interface/`, which PARITY.md
  explicitly defers to and which Checkpoint 0 already tracks.

Engineering note, not contract: the two specified sub-items justify promoting
those fixtures from informational to required, but since the meter is Dev's
artifact and a wrongly-enforced check would fail a correct meter at Checkpoint 1,
leaving them informational until a meter exists costs nothing. Astra's call.

**7. `schema_version` validation — already specified as exit 2**, by the same
"exactly the following fields" / "malformed records" pair. A record carrying a
version other than 1 does not conform to the envelope.

**8. Non-`.json` files in a directory — genuinely open.** PARITY.md fixes "one
object per `<input_id>.json`" but does not say whether a stray file is ignored
or fatal. Low stakes: Astra produces these directories and can guarantee they
contain only `<id>.json`.

**9. Nested subdirectories under `--inputs` — genuinely open.** Same class as 8,
same mitigation. It interacts with 13 only if recursion is chosen.

**10. Encoding and line endings of `mismatches.jsonl` — genuinely open,
non-gating.** The report is a diagnostic artifact; the gate is the exit status.
The harness already parses tolerantly.

**11. Exit codes above 2 — already specified.** PARITY.md enumerates 0, 1 and 2
as the meter's complete outcome set, and "A compile error, interpreter failure,
timeout, or serialization failure must not be serialized as an ordinary answer
or silently removed from the input population. The harness reports it as an
infrastructure failure; parity has not passed." Any other status, including a
signal death, is an infrastructure failure and parity has not passed. Harness
implementation responsibility.

**12. Unreadable or absent directory — already specified as exit 2.** Governing
wording: "Exit 2: unimplemented or unable to perform a valid comparison (**for
example**, malformed JSON, invalid schema, or ambiguous IDs)." The list is
illustrative, not exhaustive; an unreadable directory is an inability to perform
a valid comparison.

**13. ID case sensitivity and "ambiguous IDs" — mostly specified; one clause
genuinely open.** Case-sensitive string comparison is the default and nothing in
the contract authorises case folding. "Require exactly one output from each
engine per selected ID" and "duplicate IDs/keys ... fail with exit 2" cover the
substance. What is open is the one-line definition of "ambiguous IDs". The
case-insensitive-filesystem variant is a development-environment hazard, not a
contract hazard: the graded runtime is pinned to `linux/amd64` per
`docs/contracts/RUNTIME.md`, where the collision does not arise. It arises on
Dev's macOS, which is worth knowing while writing the meter.

**14. Shared or identical output directories — genuinely open, and the only one
of the fourteen with credibility stakes.** If `--prolog-out` and `--lean-out`
name the same directory, every comparison is an engine agreeing with itself and
Checkpoint 1 passes vacuously. "Require exactly one output from each engine per
selected ID" is precisely the clause whose application is ambiguous here. Dev
should pin it when writing the meter. Independently of that, Astra's invocation
controls the three paths: pass three distinct directories and record the
resolved absolute paths in the run log. That makes the hazard non-gating now.

### Which questions genuinely remain

Five: 8, 9, 10, 13 (the definition of "ambiguous IDs") and 14 — plus the float
sub-item of 6, which is not a new question but a consequence of the pending
result specification. Only 14 can produce a false gate pass. All five are
one-line pins Dev can make while writing the meter; none is a Checkpoint 0
deliverable, and none should be added to the checkpoint list.

### Crash / stale report versus malformed input

These are different failures and the contract treats them differently.

*Malformed input* is fully specified and needs nothing: malformed JSON, invalid
schema, wrong section, duplicate keys, unexpected IDs, stem/ID disagreement and
ambiguous IDs are all exit 2, with a reason on stderr, "never zero mismatches",
and "report the error without claiming that comparisons completed."

*The crash / stale-report problem* is a safety property, not an input question.
Two already-specified clauses bound it:
- Exit 1 means "mismatches", i.e. a comparison that ran to completion and found
  disagreements. An uncaught exception exiting 1 is therefore out of contract on
  its face; the obligation to trap unexpected exceptions and exit 2 instead
  follows from the exit-code semantics and needs no new clause.
- The stale-report risk exists only in a *reused* directory. PARITY.md already
  says the harness invokes the meter "in a dedicated run directory". A fresh
  directory per invocation makes a previous run's report structurally
  unreachable, which is stronger than any truncate-before-work rule the meter
  could implement, and it is Astra's responsibility, not Dev's.

So: no contract choice is required here. What is required is that Astra never
reuses a run directory and treats any status outside {0,1,2}, and any exit 1
without a readable `mismatches.jsonl`, as an infrastructure failure. The
harness's own `stale-report-is-cleared` fixture stays useful as a check of the
success-path truncation clause.

### The reproduced builder-tool defects

All three are restorations of existing written contracts, not human-semantic
decisions, and need no Dev approval. They are Astra's own tooling; fixing them
touches nothing under `human/`.

1. `scripts/parity_conformance.py:78` builds input records with the
   engine-output helper, emitting `result` and omitting `payload`. PARITY.md:
   "Every input record contains: `schema_version`, `input_id`, `section`,
   `payload`." A meter that enforces the input envelope would correctly exit 2
   on the all-agree fixture, so the harness would fail a *correct* meter — the
   worst failure mode for an acceptance tool. Fix: give input records their own
   builder with a `payload` key. `{}` is the minimal conforming placeholder and
   is consistent with the harness's own discipline of opaque placeholders;
   PARITY.md tells the meter it "only needs the input identity and section", so
   a meter that rejected `{}` would be enforcing an unapproved payload schema.
   That would be a finding to raise then, not a reason to guess a payload now.
2. `walk_protected()` silently omitting a symlinked directory. HASHES.md:
   "reject absolute paths, traversal components, symlinks", "Paths must identify
   regular files", "Nothing is implicitly omitted by an ignore file." A silent
   omission lets an unlisted protected path verify clean — exactly what the
   manifest exists to prevent. A symlink must be surfaced as a problem, not
   skipped.
3. Excluding every basename `HASHES.txt`. HASHES.md excludes "`HASHES.txt`
   itself", with the stated reason "a manifest cannot hash its own final
   contents". That reason applies to the protected root's self-manifest and to
   nothing else; `nested/HASHES.txt` is an ordinary protected file. `.git` is
   the only other exclusion.

Each fix should land with a negative regression fixture that the checker must
reject, and the manifest re-verified afterwards. Until then the accurate
statement of status is that the manifest verifier reports no problems on the
current tree, which is weaker than the tree being clean, because the verifier
has two demonstrated blind spots. The same reasoning applies to the interface
check: 29 guards passing against an always-true `OracleGuards` instance
establishes that the guards elaborate and type-check, not that they
discriminate. A deliberately-wrong instance that the suite must reject is the
matching negative control. Whether the production V7/V8 guards are implementable
as written is a separate question resting on the installed decisions, not on
this review.

## Rationale

The instinct behind the fourteen-item list is right — an unpinned comparator
clause lets two correct-looking meters disagree, and `parity/check.py`'s hash is
part of the Checkpoint 1 gate, so late corrections are expensive. But most of
the list re-asks questions PARITY.md answered, in some cases with a catch-all
clause ("for example", "exactly the following fields") that the reader passed
over. Treating all fourteen as open would hand Dev fourteen decisions where four
exist, and would make the acceptance harness, rather than the contract, the
specification — the failure mode the harness's own docstring warns against.

The asymmetry worth holding onto: where a clause is open *and* Astra controls
the producing side (8, 9, 10, 14), Astra can eliminate the exposure by
construction and report what it did, without waiting for Dev and without
inventing a rule. Where a clause is open and nobody controls it, it goes to Dev.
Only "ambiguous IDs" is in the second category, and it is one line.

## Contract change

No. No new rule is proposed, nothing is appended to `docs/DECISION_LOG.md`, and
none of the fourteen items is promoted to a checkpoint requirement. The three
tool corrections restore existing contracts and change none.

## Escalate to Dev

Yes, narrowly: the five remaining items (8, 9, 10, the definition of "ambiguous
IDs" in 13, and 14) are Dev's to pin while writing `human/parity/check.py`, and
14 should be pinned deliberately because it is the one that can produce a false
Checkpoint 1 pass. This halts nothing that is not already halted — the meter
lane is blocked because the meter does not exist (B006 item 1) — and no Astra
lane waits on these. No runtime-deviation approval or checkpoint waiver is
sought or granted here; both remain Dev's.
