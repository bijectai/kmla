# Q-010: A-009's proposed V10 does not cover multiple birth dates

## Phase / lane

Phase 1 / oracle specification review. Development remains paused for Dev.
This is review of a proposed remedy, not permission to alter signed semantics.

## Question

A-009 composes inequalities around a person cycle using one `dob(p)` per person.
Where do current G1/H1/H5 require that function to exist? They preserve lists,
multiplicity and all fact solutions; they do not require one birth event or
one start value per person. The pinned diagnostic below has no equal birthday
between distinct persons yet still exhausts inference budgets.

Please review and explicitly withdraw or qualify V10's sufficiency and the
proposed `2 * persons.length + 2` bound if this is a valid counterexample to
the argument. Preserve A-009 as immutable and append any correction to the log.
Give a concise corrected escalation for Dev. Do not substitute another unproved
domain/fuel rule as an approved fix; identify the proof obligation left open.
No implementation, signed decision or input filter may change in this review.

## What was tried

`docs/consult/evidence/r5_multibirth_cycle.pl` is the preceding two-sibling
fixture except that `a` has births at 2000-01-01 and 2002-01-01 and `b` has
one at 2001-01-01. No day is shared across distinct persons, even before applying
A-009's relationship-graph restriction. The source permits existentially choosing
different birth facts in different recursive calls. Year remains 2018.

The original pinned runtime was used with all source/evidence mounts read-only.
Fresh Prolog processes produced the following output (retained with exact
commands and raw diagnostics in `r5_multibirth_cycle_results.json`):

```text
no_shared_birth_date 0 'no_shared_birth_date\n' ''
age_both_directions 0 'age_both_directions\n' ''
multibirth_cycle_100k 0 'inference_limit_exceeded\n' ''
multibirth_cycle_1m 0 'inference_limit_exceeded\n' ''

```

Both `s152_c_3(a,b,2018)` and `s152_c_3(b,a,2018)` succeed in the same input.
The first uses `a`'s later date, the second its earlier date. Thus strict
inequalities on selected solutions do not imply a strict order on persons.
This diagnostic is not an original case, a generated grading input, an empty
reference answer, or a formal divergence/validity proof.

## Proposed answer

The original R5 flaw remains, but A-009's suggested V10 and its fuel argument
are not justified without an additional, unapproved functionality assumption.
Do not ask Dev to accept them as sufficient. A correct owner-approved domain
decision must cover the actual recursive call relation over all permitted fact

Adding uniqueness would itself narrow the signed domain and cannot be assumed.
