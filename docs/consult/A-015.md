Review only. Dev's Checkpoint 0 confirmation, the A installation and the Phase 1
authorization stand; no approved semantics are changed, no lane is implemented,

## Answer

The mechanism is faithful: extending V3 to supplied dates, a separate
tuple-indexed query certificate, and a decode/admission failure that halts rather
than answers are all the right shapes. **The enumeration is not sufficient.**
Three corrections, one of them material.

**The deeper correction is how the list is derived.** Scoping the check to the
sites a corpus scan happened to surface keys admission to the observed 376, while
`ValidStip` admits any well-formed stipulation and `gen/` will produce shapes the
corpus never contained. And a name-based scan is unreliable in both directions:
it misses `Start_relationship`, `End_relationship` and `s7703_a_1/5`'s `S13`,
which are dates without date-like names, and it would over-include `S19` in
`s7703_a_2`, which is an event identifier rather than a time. Roles must come
from the schema — H6.5's signature table with H2/H3's argument kinds — which is
exactly the principle point 2 already states for the codec ("fix roles so
producers cannot mislabel a Workday as a generic Term"). Point 1 needs the same
rule, and then the enumeration above falls out rather than being maintained by
hand.

### 2. The canonical decoder is pre-authorized, and it adds an unmeasured rejection

The obvious place a narrowing could hide is the round-trip: the pinned
interpreter is more permissive than canonical ISO. `day_to_stamp` splits on `-`
and calls `atom_number`, so `"2017-1-1"` parses, and `date_time_stamp` normalises
day-of-month overflow, so `"2017-02-30"` computes as 2017-03-02. A decoder that
requires a `Day.toISO` round-trip rejects both — inputs the reference program
handles.

That is not a new decision. **D2 already settles it**: "Day-of-month overflow is
normalised forward (`"2017-02-30"` behaves as 2017-03-02, probed); Valid forbids
invalid dates (V3), so the oracle never normalises. Malformed strings
(`"2017-1-1"` is accepted by `atom_number`; `"x"` makes `day_to_stamp` fail
silently) are likewise excluded by V3." The proposed strict decoder is the
implementation D2 assumes. Note what that sentence also reveals: D2's claim is
currently true only for facts, where `Day : Int` makes a malformed date
unrepresentable, and unimplemented for supplied values, which are `Term`s. The
gap Dev told you to close is precisely the unimplemented half of a signed
decision.

Two consequences to handle before dispatch rather than after:

- **Measure canonical form across the 156 stipulated files.** The stip-time audit
  covered out-of-range year slots and wildcard time slots; nothing yet reports
  whether a supplied date string in a Day-typed slot is non-canonical or out of
  V3 range. Under D2 such a case is *excluded*, which means an original becomes
  inadmissible and PLAN's Week-1 gate reads "0 mismatches / 376 − k" with `k`
  named. D2 authorizes the exclusion, so this is a measured consequence to report
  rather than a decision to take — but it must not be discovered at the gate.
- **Define the wrong-kind case.** Point 1 says a missing argument is a shape
  error and a wildcard introduces no date. It does not say what an `int` in a
  Day-typed slot is. In the reference, `split_string(2015,"-","",L)` yields a
  one-element list and the `[YS,MS,DS]` pattern fails silently — the same
  behaviour as `"x"`, so D2 puts it under "malformed, excluded by V3". Say so
  explicitly, or an implementer will reasonably pick a shape error instead and
  the two classifications will diverge in the report.

### 3. Tag handling is right, for a reason worth stating precisely

Retaining both `atom` and `str` textual tags with their original value is correct,
but not because the tag affects date comparison — it does not. `split_string/4`
accepts either, `day_to_stamp` reduces both to a numeric stamp, and
`latest/earliest` delegate to `is_before` (`utils.pl:39-56, 73-90`) rather than
to standard order, so there is no atoms-before-strings ordering hazard in the date
path. The tag matters for unification and for H4.3 round-trip identity: a
stipulated head carrying `atom '2015-01-01'` does not unify with a call carrying
`str "2015-01-01"`, and G4 makes that distinction semantic. Recording the reason
matters because "tags do not affect date arithmetic" is the fact that lets the
decoder be tag-agnostic while the *representation* stays tag-preserving, and a
decoder that normalised the tag "since it makes no difference" would break
round-trip identity.

### 4. Confirmations

- **Two mechanisms for two populations is correct.** Stipulations live inside
  `Household`, so V3 can reach them; query arguments do not, so they need the
  separate tuple-indexed certificate. The consequence worth writing at the
  definition site: `Valid`/`ValidStip` alone never certify a query, so the
  certificate has to be a required parameter of every entry wrapper, not an
  optional companion.
- **Traversing the actual argument tuple rather than a supplied list of alleged
  dates** is the same principle that made A-014's ∀-form necessary in place of a
  provider's list: never accept a producer's claim about which values it used.
- **No V8 recheck at the derived year** is right, and A-013 §4 supplies the
  argument — V5/V6/V7 are year-free, V3's year component is replaced by the
  checked constructor's own range proof, and the R5 subtree entered at the derived
  year reaches no §151 or §2 predicate, so E5 cannot arise there. That last clause
  still belongs inside the mode audit rather than being treated as established.
- **Failure disposition** matches draft line 66 and PARITY.md's
  infrastructure-failure channel: a diagnostic that halts the affected reference
  run, never an answer and never a filtered original.
- **Point 3's framing is correct**: schema completeness, internal call-site
  coverage, wildcard binding, E2 exclusion, the exact V10 decider and fuel
  adequacy are obligations on the authorized work, not preconditions for starting
  it. This scaffolding certifies none of them.

## Rationale

The pattern across the last several answers repeats here: the mechanism is sound
and the enumeration is scoped to what someone has looked at. A list of date
positions maintained by hand against a corpus scan will be correct on the day it
is written and wrong as soon as `gen/` mints a shape the 376 never contained —
and `ValidStip` admits far more than the 376. Deriving the positions from the
signature schema costs the same work once and cannot drift, which is why point 2's
own rule about roles should govern point 1.

The canonical-decoder question was the one worth checking hardest, because
tightening a decoder is the classic way a domain shrinks without anyone deciding
it should. Here D2 already decided, in the same direction, and even names the two
example strings. That converts a potential escalation into a measurement: the
rule is signed, so the only open question is how many of the 376 it touches, and
that number belongs in the Week-1 report rather than in a surprise at the gate.

## Contract change

None. D2 governs the decoder's strictness, V3 governs the bounds, and the
proposal implements both; no log entry is warranted. Two items for the Phase 1
report rather than the log: the count `k` of originals excluded by the extended
V3, if any, and the schema-derived date/year position list as the artifact that
replaces the hand-maintained one.

## Escalate to Dev

Nothing new, and nothing halts. If the canonical-form measurement over the 156

`376 − k` — that is a consequence of D2, not a decision, but Dev should see the

## Self-review

My Prolog assumptions are four, all checkable against the pinned interpreter and
three of them already probed in D2: that `split_string/4` accepts atoms and
strings alike so the date path is tag-neutral; that `latest`/`earliest` order
days through `is_before` and never through standard order, which is what removes
the atoms-before-strings hazard; that an integer in a Day-typed slot fails
silently in `split_string` exactly as `"x"` does, which is the basis for putting
it under D2's "malformed"; and that `s3306_c_10_A_ii/3` is the only clause that
manufactures a year from a Workday string. The assumption Dev should verify
hardest is the last, since the whole R8 coverage argument is scoped to it, and I
established it by reading clause bodies rather than by instrumenting a run —
which is also why the enumeration above should be regenerated from the schema
rather than trusted as my reading of it. Three failed edit cycles on one test
means stop and report.
