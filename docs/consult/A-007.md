### 2. The two acceptance issues

**(1) The relative-path invocation defect — yes, restoration.**

`main` validates `meter.is_file()` against the caller's cwd, then `run_case`
spawns `[sys.executable, "-B", str(meter), …]` with `cwd=run_directory`, so a
relative `--meter` is re-resolved against a per-fixture temporary directory that
does not contain it. CPython exits **2** when it cannot open the script file and
prints to stderr, which satisfies both assertions of every fixture with
`expect_exit=2, expect_stderr=True`. There are exactly seven such fixtures —
`empty-input-population`, `unexpected-output-id`, `wrong-section`,
`malformed-json`, `duplicate-object-keys`, `stem-id-disagreement`,
`invalid-input-id` — which is precisely the 7/20 observed. The arithmetic
confirms the diagnosis: nothing was executed.

Two facts make this unambiguously a builder defect rather than a contract
question. The suite's own docstring documents relative invocation
(`--meter docs/contracts/parity/check.py`), so the tool is broken against its own
published usage. And `verify_phase0.sh:130` passes `"$ROOT/human/parity/check.py"`,
an absolute path, so the same suite behaves differently depending on how the
caller spells the argument — a harness whose verdict depends on that is not
measuring the CLI contract at all.

Fixing it is restoration: resolve the meter to an absolute path before spawning
(validate `is_file()` on the resolved path), and report a failure to invoke as a
distinct harness error — never as a case result. That changes no fixture's
expected exit code, no expected mismatch IDs, and no informational/enforced flag.
Dev's instruction not to adjust the suite to reconcile a meter divergence is not
engaged: no meter ran, so there is no divergence to reconcile. The one authorized
fixture change remains the `invalid-input-id` promotion under policy 4.

Two limits to carry into the eventual run report. The exit-2 fixtures pass on any
nonempty stderr, which is what PARITY.md requires ("Print the reason to stderr")
and should not be tightened — but it means the suite cannot distinguish a correct
rejection from an unrelated failure, which is exactly why invocation errors must
be surfaced separately. And the staged stub, which exits 2 unconditionally, will
legitimately pass all seven exit-2 fixtures after the fix; 7/20 is evidence about
nothing. `verify_phase0.sh`'s "staged stub is still a stub" check is satisfied
before and after, for different reasons.

### 3. Flags in the five policies (not resolved)

**(a) One genuine omission, in policy 1, and it is load-bearing.** Policy 1's
ignore rule is scoped by "only … dot-prefixed"; policy 2 covers entries that are
not regular files. An entry that is a **regular file, not dot-prefixed, and does
not end in `.json`** — `README`, `notes.txt`, `mismatches.jsonl` — is assigned no
outcome by any of the five policies. It cannot be installed mechanically, because
the installer must choose between ignoring it and exit 2.

Policy 5's own rationale bears on it: "the meter's own report can't land inside an
argument directory and **poison the next run under policy 1**". `mismatches.jsonl`
is exactly the unassigned case, and for it to poison anything, policy 1's default
for non-`.json` entries must be exit 2, with dot-prefixed non-`.json` entries as
the carved-out exception. That reading is implied by Dev's text and is internally
consistent, but I am flagging it, not adopting it: one line from Dev settles it,
and until then policy 1 should be installed with this case marked open rather
than silently decided in either direction.

**(b) Policy 1 / policy 2 ordering — no conflict, but the qualification must
survive installation.** Apply the name test first, the type test second. The
substantive consequence of "dot-prefixed directories are covered here, not by
policy 2" is that a dotted directory not ending in `.json` (`.cache/`, `.git/`)
is **ignored**, where policy 2 alone would make it exit 2. A dotted entry ending
in `.json` reaches exit 2 through the grammar whether it is a file or a
directory. Do not collapse the two tests into one type-first check.

**(c) Sequencing, policy 4 versus the stated order.** Policy 4 lands a grammar
narrowing — IDs unique within a section under ASCII case folding — "before
Checkpoint 1", while the sequence implements and installs the meter now and
regenerates `human/HASHES.txt` at Checkpoint 0. `docs/PLAN.md` Checkpoint 1 makes
"parity/check.py hash unchanged" part of the gate. Either the grammar line lands
in PARITY.md before Dev writes the meter, or expect one meter edit and one
manifest re-pin between the checkpoints. Cheapest is to land it first. Dev's
call; no policy conflicts with another here.

**(d) The suite will not establish the five policies.** It has no fixture for
policies 1, 2 or 5, and none for policy 3's byte-level requirements (LF,
trailing newline, `ensure_ascii` off, fixed key order) — `read_mismatches`
tolerates CRLF, blank lines and a missing final newline. Dev authorized exactly
one fixture change, so a green run must be reported as establishing the
pre-existing PARITY.md envelope only, with the five policies uncovered. Adding
coverage is a suite change Dev has not authorized: propose it, do not apply it.

**(e) Two dependencies worth recording, neither a conflict.** Policy 3's
three-valued report reading (absent = infrastructure failure) is sound only in a
fresh run directory, which is PARITY.md's "dedicated run directory" clause and
Astra's obligation, not the meter's; the existing `stale-report-is-cleared`
fixture remains correct under policy 3. And policy 2's "wrap the whole run so an
unexpected exception re-exits 2" closes the meter-side half of item 2 of the
fourteen; the never-reuse-a-run-directory half stays with Astra.

**(f) Where the fourteen now stand.** Policies 1–5 close items 9, 10, 13 and 14,
and item 8 except for the omission in (a). Item 6's envelope-defect

## Rationale

reasons in that text — why upstream was rejected on path dependence, why
emulation is not banned, why archival has three legs — are the parts that a
reader six months from now cannot reconstruct and that a paper reviewer will ask
about. The acceptance-is-not-completion line is there for the same reason: an
accepted obligation and a discharged one look identical in a status index unless
someone writes the difference down.

On both acceptance issues the dividing line is the same one A-005 used. Making a
tool actually exercise the contract it claims to exercise is restoration and
needs nobody's approval. Changing what counts toward a gate that Dev has
personally defined is not, however obviously broken the accounting is — the
remedy is to report it, propose the split, and run the tool unchanged meanwhile.
