### 1. What the probe refutes

H4.2 states step (ii) as a complete procedure and gives its own justification:
rules of this shape "raise `instantiation_error` when called with the event
unbound and behave as facts when it is bound". `tax_case_33.pl:29-31` is a
counterexample to that justification, not merely a case it fails on:

```prolog
purpose_(Payment_event,Service_event) :- split_string(Payment_event,"_","",[Xp,Yp,Zp]),
    split_string(Service_event,"_","",[Xs,Ys,Zs]),
    Xp=="payment",Xs=="workforalice",Yp==Ys,Zp==Zs.
```

Both positions are event-typed, and the body requires *both* bound. H4.2's
prescribed mode — event position bound, other position free — makes the second
`split_string/4` uncallable, which is exactly what your probe reports. The
design assumption behind step (ii) is that a binary event predicate is an
*attribute* of one event; this clause is a *relation between two events*, and
H4.2 has no rule for that class.

Three supporting points, each checkable:

- **It is not G6.** The case's own directive succeeds under the pinned image; the
  raise occurs only inside our grounding construction. G6 and the V-rules concern
  the reference program's behaviour on an admitted query. Classifying this as
  reference-undefined would convert a harness defect into an input exclusion,
  which is the one move the stop-and-report standard exists to prevent.
- **An empty list would be wrong here, not merely unauthorized.** `:13-14`
  defines 87 `workforalice_2015_*` service events and `:26-27` the matching
  payments, so the clause's true ground extension is the 87 pairs
  `(payment_2015_k, workforalice_2015_k)`. Dropping the clause loses all 87 and
  changes the quantity the case asks for. This case therefore *does* discriminate
  between a lossless and a lossy remedy, which is worth knowing because a case
  with an empty extension would not have.
- **H4.2 already tells you what to do with this.** "A grounding that raises or
  fails to terminate is a finding." It authorizes the report you made. It does
  not authorize a repair, and P-INTENT clause 1 does not supply one either: it
  fixes the *direction* — the harness is under our control, so choose what
  reproduces the authors' results — while leaving the domain, the order and the
  completeness argument undetermined, and each of those changes the Household.

What *is* already signed is the acceptance test. H4.3(a) and (b) will catch a
lossy remedy, so Dev is choosing a procedure, not a criterion.

### 2. The smallest decision Dev must make

> For a binary event-predicate clause that raises when only the event position is
> bound: which domain enumerates the other position, and in what order are the
> resulting facts appended?

The option space, stated without selection:

- **(A) the event universe from step (i).** Complete for `tax_case_33`, where
  position 2 ranges over service events, and incomplete in general: H3 gives
  `purpose_/2` position 2 the roles "purpose string | service | place", and
  neither strings nor places are events.
- **(B) the event universe together with an active domain** of ground terms drawn
  from the case's and statutes' literals of the relevant argument kind. Larger,
  and still an over-approximation of the Herbrand universe, so it still owes a
  completeness argument for clauses that *construct* terms (`atom_concat`) rather
  than *test* them.
- **(C) a per-clause mode-directed procedure**, distinguishing positions the body
  generates from positions it requires bound, and enumerating only the latter.

I am not recommending among these, and the reason is not procedure: which one is
lossless depends on facts about the corpus that the audit can measure and I have
not, and the choice fixes what a `Household` *is* for 59 rule-bearing files.

### 3. Obligations any remedy must discharge

1. **Completeness per clause**, not by appeal to a Cartesian product. Your
   proposed answer is right that enumerating a product is a procedure, not an
   argument. The argument needed is: no ground solution of this clause lies
   outside the chosen domain.
2. **Order and multiplicity.** H1's "source order" is undefined for rule-derived
   facts, so the amendment must *define* the iteration order for the second
   position rather than inherit one, and keep duplicates. Without this, H4.3(a)
   is not reproducible across runs.
3. **Termination and cost.** The enumeration is `|U|²` per binary predicate —
   157² here — and must be bounded and measured. A procedure that is correct but
   quadratic on every case is a schedule fact Dev should see before choosing.
4. **Both H4.3 checks re-run over all 376**, not only over `tax_case_33`. A
   remedy validated on the case that exposed the defect is the classic way the
   next witness arrives a day later.
5. **No source repair, no clause reordering, no case exclusion, no empty-list
   exception** — all four already prohibited, listed so the amendment carries them.

### 4. A second gap the same amendment should settle

Step (ii) binds position 1 to each event. Applied to the bodyless wildcard fact
`purpose_(_,"agricultural labor")` (`s3306_a_2_B_neg.pl:75` and its `_pos` twin,
the two facts H2 names), it returns one solution per event and so expands a
single wildcard fact into `|U|` ground facts.

I want to be accurate about how strong this is: it is **not** demonstrably lossy
under H4.3. If every statute call binds position 1 to an enumerated event — which
H2 asserts — then a consistently expanding procedure satisfies both (a) and (b).
What it does is contradict the representation H2 and `Interface/` deliberately
chose, where that fact is `Fact.purpose_ (Pat.wild id) (Term.str …)`, and make
`Pat.wild` dead for the originals. So it is a design question rather than a
proven defect — but it is a question about the same sentence of H4.2, and
answering it separately later means amending H4.2 twice.

## Rationale

The distinction that decides the first question is between a decision that is
*under-specified* and one that is *refuted*. H4.2 is not silent about this class
of clause; it asserts a property of it — raises when unbound, behaves as a fact
when bound — that is false for a relation between two events. A builder cannot
patch a refuted premise by choosing the enumeration that makes the current case
pass, because the choice fixes the contents of every rule-bearing Household and
because the obvious choice, the event universe, is provably incomplete for the
very predicate that exposed the defect.

The part worth insisting on is obligation 1. Every remedy in the option space
*produces* a finite set of facts, and each will make `tax_case_33` succeed. What
distinguishes them is whether they can be shown to miss nothing, and that
argument has to be made per clause against H3's argument roles. This is the same
shape as A-014's list-versus-∀ correction: a procedure that enumerates is not, by
itself, evidence that the enumeration is exhaustive.
